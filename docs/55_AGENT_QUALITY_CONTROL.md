# 55 — Agent quality control and blind visual review

**Status:** operational foundations + proposed integrations. The architecture
guard and blind-pair harness below are implemented; Thessa-native headless
screenshot capture, autonomous image judging and hardware performance gates
are **not** implemented by this document.

## Workflow contract

1. **Orient.** Read root `AGENTS.md`, `docs/00_STATUS.md`, the relevant ADR
   and subsystem docs. Trace existing producers/consumers before adding a path.
2. **Simplify first.** Load `.agents/skills/ponytail/SKILL.md` and apply
   its smallest-complete-change ladder. It does not override Thessa's
   physical, numerical or safety invariants.
3. **Preserve the complete solution.** Never trade away physical causality,
   numeric error envelopes, fallbacks, diagnostics, input handling, test
   coverage, or measured performance just to reduce LOC.
4. **Verify.** Run relevant crate tests and reference cases, then architecture,
   integration, visual and performance checks according to the changed surface.
5. **Report evidence.** Give exact command(s), output or artifact location,
   baseline commit, scenario, GPU/driver when relevant, and known omissions.
   Never label an unexecuted check as passed.
6. **Integrate.** Keep a buildable tree; update status docs in the same change.
   A code-producing agent cannot self-certify its own visual comparison.

## Commit scopes (adapted from Telegram Desktop)

Prefix a commit with `[ai] ` **only** when every retained change and the
purpose are agent infrastructure: agent instructions, testing harness,
review prompts, task templates or agent-runner tooling. This prefix is **not**
an authorship marker. Regular gameplay, renderer, simulation and product CI
changes use ordinary commit titles even if generated by agents. Split a mixed
change into separate commits where practical. Do not rewrite unrelated author
metadata or attach bogus co-author trailers.

## Executable architecture rules

`python3 tools/agent-qa/check_architecture.py` inspects Cargo metadata. It
fails on selected backend/runtime dependencies in canonical foundation crates
and MIT workspace crates depending directly on GPL workspace crates. It is
run by CI; type-level boundaries and indirect external license obligations
still require explicit review.

## Blind visual arena

The blind harness is `tools/agent-qa/arena.py`. It accepts matched screenshots
from Thessa versus a reference game, or a before/after pair from Thessa.
Unlike pixel-diff regression tests, it measures **subjective preference**;
it does not prove physical correctness or numerical fidelity.

- Input: a TOML list of scene IDs, two actual PNG paths and their private
  origins. Keep source images, test assets and licenses lawful and documented.
- `prepare` validates PNG dimensions/chunk CRCs, strips identifying ancillary metadata,
  shuffles A/B per scene, copies
  the frames to a blind review directory and places the origin key elsewhere.
- Reviewers (human or model) see only unlabeled `A.png` and `B.png`, the
  `cases.json` metadata and `REVIEW.md` rubric. No model is invoked by the tool.
- Record exactly one vote per reviewer and scene: A, B, tie or invalid.
  Score only with the private key *after* reviewer decisions are frozen.
- Record explanations under lighting, atmosphere, silhouettes/LOD, temporal
  artifacts, physical plausibility and confidence. Treat mismatched camera,
  FOV, HDR/exposure, time of day, scene content or HUD as **invalid**.
- Re-run with swapped orientation/several seeds and report ties/uncertainty.
  Long-term ranking (e.g. Bradley–Terry) requires sufficient connected
  comparisons and is not currently implemented.

This is deliberately **different** from golden scene regression. Golden
scenes must eventually replay fixed simulation seeds, camera trajectories,
render settings and timestamps against structural/numeric oracles and visual
thresholds. Such a capture bridge is future work and must not be inferred
from the current Bevy remote MCP configuration.

## Proposed native control bridge (not implemented)

A future headless-first `thessa-control` should expose one typed command/query
registry to CLI, MCP and test clients. Intended operations include
`sim.load_scenario`, `sim.step`, `sim.inspect`, `render.set_camera`,
`render.capture`, `terrain.inspect_lod`, `terrain.inspect_residency`, and
`perf.capture`. Keep authoritative simulation independent of rendering.
Require loopback authentication, an explicit read/write distinction, bounded
inputs, sandboxed file output locations and no unrestricted shell execution.

The existing `bevy_brp_mcp` integration is a temporary client adapter, **not**
an implementation of this native contract.

## Performance evidence (future automation)

When implementing native telemetry/gates, keep time budgets per fixed scene,
resolution, graphics quality, renderer and GPU/driver. Capture CPU simulation,
CPU render preparation, GPU frame time, streaming queue age, upload volume,
LOD changes and stutter p99. Compare with a same-machine baseline before
claiming gains; tolerate timing noise. The current CI **compiles** many
benchmarks but does not enforce a new runtime budget based on this document.
Do not copy arbitrary PhotoCraft thresholds into a space simulator.

## Low-cost two-machine development

- **Machine A:** author a scoped change, run incremental compiler/tests,
  produce a commit or isolated worktree.
- **Machine B:** build that exact commit; run scenario replays, visual capture
  and/or GPU tests; emit artifacts and hardware metadata. This does not
  require a second simultaneous paid agent.
- Share source through Git and diagnostic artifacts explicitly. Do not share
  writable build outputs or let two agents edit the same working tree.
- An independent reviewer (human or model) examines failures and blind images
  *without* the implementer's preferred answer or the origin key.
